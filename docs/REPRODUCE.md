# Как воспроизвести анализ

Диалект SQL — SQLite. Запросы можно выполнять в DBeaver. Python используется для графиков и отчёта.

## Пять файлов вместо отдельных этапов

| Файл | Содержание | Прежние этапы |
| --- | --- | --- |
| [00_setup.sql](../sql/00_setup.sql) | Создание пяти таблиц и индексов | 00 |
| [01_data_quality.sql](../sql/01_data_quality.sql) | Импорт, дубликаты, связи, пропуски категорий, состав заказов, конец периода | 01–06 |
| [02_repeat_purchases.sql](../sql/02_repeat_purchases.sql) | Полнота окна, витрина покупателей, общий показатель, месяцы, одновременные первые заказы | 07–11 |
| [03_first_categories.sql](../sql/03_first_categories.sql) | Первая категория, показатели всех категорий, сумки и Cool stuff по месяцам | 12–14 |
| [04_delivery.sql](../sql/04_delivery.sql) | Даты и группы доставки, месяцы и категории, два расчёта после получения, итоговая выгрузка | 15–19 и дополнительные проверки |

Повторяющиеся расчёты общей метрики и месячных групп используют `buyer_retention_180`. Определения повторной покупки, категорий и доставки сохранены. Прежние файлы доступны в [истории до объединения](https://github.com/Alina-lab/ecommerce-retention-analysis/tree/9c9e857eedba69c3a2330b3820c183ce1c62426b/sql).

## 1. Создать таблицы и импортировать данные

Создать локальную базу SQLite и выполнить `sql/00_setup.sql`. Если база уже содержит данные проекта, повторный импорт не нужен.

| CSV из датасета Olist | Таблица SQLite |
| --- | --- |
| olist_orders_dataset.csv | orders |
| olist_customers_dataset.csv | customers |
| olist_order_items_dataset.csv | order_items |
| olist_products_dataset.csv | products |
| product_category_name_translation.csv | category_translation |

В DBeaver импортировать CSV в существующие таблицы, сопоставив колонки по заголовкам. Идентификаторы, даты и почтовые префиксы сохраняются текстом. Не создавать таблицы заново через автоматическое определение типов.

## 2. Проверить импорт

Выполнить `sql/01_data_quality.sql`. Число строк должно совпадать с исходными файлами; проверить дубликаты ключей и потерянные связи. Отдельно показаны пропуски категорий и неполные крайние месяцы.

В проверке популярности категории один заказ может попасть в несколько категорий. Строки этого результата нельзя суммировать как количество уникальных заказов.

## 3. Выполнить аналитические расчёты

Запускать в порядке `02_repeat_purchases.sql` → `03_first_categories.sql` → `04_delivery.sql`. Скрипты пересоздают только аналитические VIEW; исходные таблицы и данные не удаляются.

Контрольные результаты текущего проекта:

| Проверка | Значение |
| --- | --- |
| Покупатели с полными 180 днями | 49 452 |
| Повторные покупатели за 180 дней от первой покупки | 1 358; 2,75% |
| Группы первой категории | 74 |
| Доставка вовремя / с опозданием / неизвестно | 46 651 / 2 799 / 2 |
| Ближайший повтор до полного получения или одновременно с ним | 526 |
| После получения, внутри исходных 180 дней: вовремя / опоздание | 823 из 46 651 / 35 из 2 799 |
| Полные 180 дней после получения: вовремя / опоздание | 829 из 44 279 / 32 из 2 332 |

Последний SELECT в `04_delivery.sql` даёт одну строку на покупателя. Экспортировать его в CSV с заголовками как `data/buyer_analysis.csv`. Отдельный импорт этой выгрузки в SQLite для дополнительных проверок больше не нужен: они используют аналитические VIEW.

## 4. Собрать графики и отчёт

Из корня проекта:

```bash
python -m pip install -r requirements.txt
python analysis/build_report.py --input data/buyer_analysis.csv --output reports
```

Скрипт проверяет уникальность покупателей, флаг повтора по датам, полноту окна и контрольные значения выгрузки. Из неё пересчитываются категории, месяцы и основной показатель доставки.

Два дополнительных расчёта после получения используют подтверждённые SQL-агрегаты в `analysis/delivery_checks.json`. Они требуют всех последующих заказов, поэтому восстановить их из одного `next_purchase_at` нельзя. При смене исходных данных выполнить соответствующий блок `04_delivery.sql` и обновить эти агрегаты.

Графики сохраняются в `reports/charts` как PNG и SVG, таблицы — в `reports/tables`. HTML сохраняется как `reports/olist_report.html` и открывается без интернета. Его текст находится в `analysis/report_template.html`, оформление графиков — в `analysis/charts_style.py`.

Текст и контрольные значения описывают текущую выгрузку. При смене периода или правил расчёта их нужно пересмотреть.

## Проверки после объединения

- Основная витрина и доставка пересчитаны на исходных orders/customers и сверены с buyer_analysis.csv.
- Категории проверены на примерах с одной категорией, несколькими категориями, пропуском и отсутствием товарной позиции. Их SQL-определение сохранено из прежнего проекта; полные исходные order_items/products/translation в этой рабочей сессии недоступны.
- Проверены одновременные первые заказы, повтор ровно через 180 дней и на секунду позже, получение в обещанный календарный день и ошибочная дата.
- Полный результат итоговой выгрузки сверяется с buyer_analysis.csv с использованием ранее подтверждённых категорий из этой выгрузки.
